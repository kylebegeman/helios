Helios Direction

Helios hosts any software on a VPS, and makes the next VPS cost almost nothing. There are no more milestone releases. It stays on 0.7.x and ships one feature at a time. Helios is the product name; installed services and data retain their established identities for compatibility.

This replaces the release ladder in the 0.7 plan, which is delivered and closed. The backlog is still Ideas.

The change

No 0.8, no 0.9, no date for 1.0

The plan had four rungs: 0.7 runs the personal machine, 0.8 wires Loom, 0.9 opens the launchpad, 1.0 keeps the promise. 0.7 is done. The rest is cancelled as a sequence.

Helios stays on 0.7.x. Each finished feature is a patch release, cut when it is finished rather than when a group of things is finished. 0.7.2 was the build cache bounded and garbage collection scheduled, and that was the whole release. That is the size a release is allowed to be.

1.0 is still a real bar: a stable manifest, a stable API, upgrade guarantees, a security review and written docs. It is no longer a release that work aims at, and nothing is being sequenced to reach it.

Why

The milestones were solving a problem that does not exist here

A version ladder is how you tell other people what to expect and when. Nobody is waiting on this. It is private infrastructure with one user, and the only real deadline it ever had, moving off the Python estate before something else broke, has passed.

What the ladder cost was real. Work got picked by which rung it sat on rather than whether it was worth doing, which is how the fleet view came to be the next large thing on the list without anyone having asked what it was for. Grouping features also meant nothing shipped until the slowest one in the group did.

Against that, a patch per feature means a change is on both machines the day it is written, and a mistake in it is one feature wide. The build cache fix found two further bugs within an hour of being on a real machine, because it was on a real machine.

Purpose

What Helios is for

Take any piece of software, put it on a VPS, and keep it alive without thinking about the VPS.

Not a Loom deployer. Loom is the largest thing it hosts and the reason it was built, but it is one app in a manifest like any other, and nothing in Helios knows its name. The personal sites, braintreelabs.io and anything else are the same shape.

The shape of the work is several businesses and several SaaS products, each one getting its own VPS so that its workload, its storage and its blast radius belong to it alone. That means buying a machine is a routine act, not an event, and the thing being deployed onto it is almost always a web app, an API or something else server-side.

Two things follow, and they are the whole roadmap. Any software means the manifest describes the thing without special cases, and starting a new one is quick. Any VPS means machine number nine costs the same as machine number two: buy it, point Helios at it, deploy. Keep it alive is the floor under both, and it is the part that already works: backups that restore, certificates that renew, and a machine that cleans up after itself without being asked.

Gap one

Any software: mostly solved

The manifest already describes more than anything currently deployed uses. The obstacle was never that Helios could not express a new app, it was that expressing one meant opening an existing app's helios.yaml and copying from it, with nothing in the repo to copy from.

helios init closed that in 0.7.3. It writes a commented manifest for a web, static, worker or cron app, adds a database on request, and validates what it wrote before it reaches disk, so a generated manifest always loads.

helios init api --host api.example.com --postgres

The generated editor schema and helios check now pair with init to validate manifests and source inputs before deployment.

What is left:

  • Redis or Valkey as a declared data service, the way Postgres is. It is the one dependency common enough that hand-rolling it as a worker with a volume will keep coming up.
  • An adopt path for software with no Dockerfile. Today the answer is to write one. Whether Helios should ever generate one is an open question, not a plan.
Gap two

Any VPS: make the next one cost nothing

Every VPS worth buying runs Ubuntu or Debian, and helios host setup takes one from bare to ready in a single command. The distribution is not the problem. The problem is everything around it.

Targets and bootstrap now cover the repeated setup: a profile pins the binary and host settings, while sealed integration transfer carries selected configuration to the target identity. The target connection, machine, source and approval remain bound through the workflow.

Use safe moves for an app and machine recovery for a lost host. Both make readiness private before an explicit cutover. Access to the backup repository and protected recovery material remains a prerequisite.

The ongoing work is keeping those paths proven: run the disposable Linux lane for runtime, bootstrap, transfer and recovery changes, preserve its target-safety guards, and report external prerequisites separately from passing proofs. New providers or a different deployment experience are product choices, not missing wiring in the existing bootstrap feature.

Two things are deliberately not on this list. Distributions beyond Debian and Ubuntu, because nothing needs them and a second package manager is a second setup path forever. And running on a machine in a home rack: it needs an inbound path from the internet that a racked machine does not have, and it is a fun experiment rather than something a business depends on. If that changes, it changes because the rack got a public address, and this page gets revisited then.

Not doing

The fleet view, and why it is tabled

Item 32 was the next large thing on the old ladder: every machine enrolled with Loom over a mutually authenticated outbound link, with Loom showing every machine, app, deploy, backup, drill, alert and log, and approvals happening there.

It is tabled for as long as the estate is two machines. A fleet view is a way to see more machines than you can hold in your head, and two is not that number. helios status over SSH answers every question it would answer. The other side of the trade is an enrollment protocol, signed and scoped commands, replay protection, a cursored event stream and a new mode in Loom, all of which then have to keep working forever.

Revisit it when there are enough machines that forgetting one is plausible, or when someone without an SSH key needs to see the estate. Everything that depended on it is tabled with it: the Core's own lifecycle from inside the app, push alerts, and approval records for agent-run operations.

Working agreement

How work gets picked now

  • One feature, one patch release. It reaches every machine when it is done, not when a group is done.
  • A feature is picked because something is currently annoying or currently broken, not because of where it sits in a list. Ideas is a menu, not a queue.
  • A feature counts as done when it has run on a real machine. Two of the four bugs in the 0.7.2 work were invisible until then.
  • Nothing is built for a fleet, a team or a user who does not exist.
